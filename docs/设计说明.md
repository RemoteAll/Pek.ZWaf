# Pek.ZWaf 设计说明与移植对照

> 决策记录（含用户原话）与两个参考实现的逐项对照。改行为前先看这里。

## 1. 背景与目标

用户原话（2026-11-17）：

> 「G:\Code\Rust\Pek.RWaf 和 G:\Code\Pek.FrameWork\Pek.WAF 这两个项目你要帮我参考一下，
> 我要使用 zig 来实现同样的功能并会用到 zig 开发的项目中的。」

目标：*功能*（不是逐行 API）对齐两个参考实现，产出可在 zig 生态（`zzig` 之上）直接消费的公共库。

## 2. 两个参考实现的定位差异

| | C# `Pek.WAF` | Rust `Pek.RWaf` |
| --- | --- | --- |
| 形态 | ASP.NET Core 中间件 | 公共库 + `dhrust` 中间件 |
| 核心 | **规则引擎**（`MRE`：反射 + 表达式树编译 Ruleset JSON） | 在 C# 规则格式之上扩展：爬虫分级、攻击特征、CC 限速、接口级限流、统计 |
| 配置 | appsettings（`IOptionsMonitor<Rule>`） | `Config/Waf.toml`（JSON 旧格式自动迁移） |
| 频控 | 每 IP 10 次 / 5 分钟（仅监控日志） | CC 每 IP 60 秒固定窗口（429） |

结论：**功能集合以 Rust 版的决策链为准**，规则格式以 C# 版为准（两边本就共用）。

## 3. 逐项移植对照

| 能力 | Rust 实现 | Zig 实现 | 说明 |
| --- | --- | --- | --- |
| 决策链顺序 | `middleware.rs::check_inner` | `waf.zig::decide` | 顺序逐项一致（签名 → 开关 → 回环 → IP 名单 → UA → 爬虫 → 攻击 → 规则 → CC） |
| 请求视图 | `wafreq.rs`（owned String + 复用覆写） | `wafreq.zig`（**借用切片，零分配**） | Zig 字符串是切片，不需要复写缓冲 |
| IP 匹配 | `wafreq.rs::ip_match` | `wafreq.zig::ipMatch` | 精确 / CIDR / 通配符 / 列表 / 文件 |
| 爬虫分级 | `bots.rs`（6 类 + 130+ 关键词 + TinyMemo） | `bots.zig`（同名单 + `threadlocal` 8 槽 memo） | 分类顺序一致 |
| 攻击特征 | `attack.rs`（规范化 + 双重解码 + 位掩码） | `attack.zig`（同名单、同规范化口径） | 位掩码、静态资源只查路径穿越一致 |
| 规则引擎 | `rules.rs`（serde + `regex` crate） | `rules.zig`（`std.json` + vendor 正则） | 操作符全集一致，含 `IsBotKind` |
| CC 限速 | `dhrust::ratelimit::WindowLimiter` | `ratelimit.zig::WindowLimiter` | 「每 key 首次命中起 60 秒」口径一致；条目上限 65536 |
| 接口级限流 | `throttle.rs`（70 KB） | `throttle.zig` | 7 策略 / 多阀门 / WhenNull / 429 三格式 / 规则匹配 `{param}` |
| 统计 | `stats.rs`（原子 + 固定 Top 表） | `stats.zig`（同结构，**快照为值类型**） | Top IP 16 / 原因 8 / 分钟桶 6 |
| 热重载 | `RwLock<WafConfig>` + mtime 10s 节流 | `gen.zig` 引用计数配置代 + mtime 10s 节流 | Zig 侧配置是切片，必须靠引用计数保证生命周期 |
| 早拒 | `HttpServerOptions.early_guard` + `check_head` | `ServerGuard`（包装 `http_server.Server.handler`） | 语义一致：不读 body 就拒绝 |
| 可信签名 | `TimeStamp/Nonce/Signature` + SHA1 | 同算法（`std.crypto.hash.Sha1`，升序拼接） | 与 C# / dhrust 字节级一致 |
| CSRF | `csrf_reason` | `csrfReason` | 同判定顺序（Sec-Fetch-Site → Origin/Host → 无来源头放行） |
| XFF | `client_ip_behind_proxy`（末段） | `Waf.resolveClientIp`（末段） | 仅对端回环 + 开关打开时采纳 |

## 4. 有意的差异（全部有理由，不是遗漏）

1. **规则集文件格式**：Rust 把 Ruleset 塞进 `Waf.toml` 的 `ruleset` 字段；Zig 用独立
   `rulesetFile`（JSON）。原因：规则是递归树，TOML 内联表/数组表表达力差且易写错；
   C# 本来也从 JSON 读，独立 JSON 更贴近「双端共用同一份规则」。
2. **接口级限流配置用 JSON**（`Config/Throttle.json`）：两层数组（规则 → 阀门），
   同理由；WAF 主配置仍是 TOML。
3. **`whenNull=intercept` 的空值标识**直接用客户端 IP（Rust 为 `empty_value_<md5_short(ip)>`）：
   目的相同（同源共用计数），少一次哈希。
4. **`jsonDgResult` 省略 `operationTime` / `id`**：动态时间字段；需要时宿主可自行覆盖响应。
5. **客户端 IP 未知时不做 CC 计数**（`ip == ""`）：否则所有未知来源共用一个桶，
   一个客户端就能打满全站配额。zzig `http_server` 的请求视图目前不带对端地址，
   走 `App` 集成时属于这种情况——补上 `remote_addr` 后自动恢复按 IP 限速。
6. **路由中间件不覆盖未匹配路径**：zzig 的 `dispatch` 先匹配路由再跑中间件，
   所以 `/.env`、`/x.php` 这类探测要靠 `ServerGuard` 在本层提前拒（Rust 侧对应 early_guard）。
7. **配置字段缺失时继承「调用方预设」**：`zzig.config.toml.decode` 从类型默认值起步，
   会把 `publicSite()` / 项目的 `skipBotPrefixes` 静默清空（Rust 2026-10-21 踩过：
   直连 RestSharp UA 被误拦）。本库因此**不用 `decode`**，改为「以预设为起点、逐键覆盖」。

## 5. 复用与不复用（检索证据）

复用：
- TOML 解析 → `zzig.config.toml.parse`（不重写解析器）；
- 日志 → `zzig.Logger`；
- UNIX 时间 → `zzig.compat.nanoTimestamp`（0.17 已移走 `std.time.timestamp`）；
- 互斥量 → `zzig.compat.Mutex`（0.17 已移除 `std.Thread.Mutex`）；
- 请求/路由/响应模型 → `zzig.web.router`、`zzig.http_server`；
- 正则 → `ZZUI/src/regex.zig`（554 行回溯引擎，带步数上限）。**字节级拷贝**到
  `src/vendor/regex.zig`（SHA256 已核对），原因：ZZUI 是 GUI 工程，为一个正则把 Win32 依赖
  拉进服务端进程代价太高；且在别人的仓库里下沉需要单独确认。
  **同步纪律**：ZZUI 侧改了要同步拷过来，或后续下沉到 `zzig` 后改为依赖。

不复用（附原因）：
- `zzig.Net.parseCidr`：实测在 `/0`（`0.0.0.0/0`）上 `@intCast(32 - prefix_len)` **panic**
  （u5 装不下 32）。WAF 必须容错而不能崩进程，故在 `wafreq.zig` 内自实现等价解析，
  并正确处理 `/0`、非法前缀退化精确匹配。**建议 zzig 侧修复后可切回。**
- `zzig.url.decode`：非法转义直接报错；WAF 需要「重容错扫描」（攻击者故意写坏的转义必须
  原样进入特征匹配），故自写 `percentDecodeInto`。
- `zzig.config.toml.decode`：见 §4.7。

## 6. Zig 0.17 迁移踩坑（写在这里省下下次的时间）

| 坑 | 现象 | 结论 |
| --- | --- | --- |
| `std.Thread.Mutex` 移除 | `root source file struct 'Thread' has no member named 'Mutex'` | 用 `zzig.compat.Mutex`（spinlock + yield） |
| `std.time.timestamp/milliTimestamp` 移除 | 同上 | 用 `zzig.compat.nanoTimestamp()` 换算 |
| 文件 IO 全部要 `Io` | `std.fs.cwd()` 不存在 | `std.Io.Dir.cwd().readFileAlloc(io, ...)` / `createFile(io, ...)` / `file.close(io)`；测试用 `std.testing.io` |
| `ArrayList.writer` 移除 | `no field named 'writer'` | 非托管 `ArrayList` 用 `out.print(gpa, fmt, args)` |
| `std.fmt.fmtSliceHexLower` 移除 | — | `std.fmt.bytesToHex(digest, .lower)` |
| `**` 数组重复语法变更 | `binary operator '*' has whitespace on one side` | 0.17 里 `**` 的右操作数改成类型；改用 `@memset`/循环构造 |
| `std.json` 字符串别名输入 | 规则 `name` 变乱码（0x55） | **解析文本必须分配在 arena 上**，不能 `gpa` 分配后释放 |
| `b.args` 移除（build.zig） | `no field named 'args'` | 用 `b.option`/固定参数 |

## 8. 100 万口径性能基准（2026-11-18）

命令：`zig build bench -Doptimize=ReleaseFast`（Windows / Zig 0.17.1；单线程；`ReleaseFast`，
Debug 数字无参考价值）。基准源码 `bench/waf_bench.zig`。

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| allow: browser GET | 6826.8 ns | **365.6 ns** |
| block: sqli query | 3990.9 ns | **510.5 ns** |
| block: malicious UA | 238.6 ns | 247.0 ns |
| allow: static asset | 1429.6 ns | **272.0 ns** |
| allow: POST 8KB body | 未跑完（82 × 8 KB × 100 万 ≈ 656 GB） | **23.98 µs** |
| 1M IP 黑名单 miss | O(n) 字符串解析 | **204.5 ns** |
| 1000 条规则 miss | — | **3.20 µs** |
| CC 计数开启 | — | **214.9 ns** |
| Stage 复用（当前中间件路径） | — | **349.1 ns** |
| Stage 每请求新建（旧路径） | — | **3257.6 ns** |
| 分片限流器（8 线程，key 分散） | — | **23.3 ns/次（4286 万次/秒）** |

> 注：Stage 对比用的是 bench 的 `std.heap.page_allocator`（每次分配走系统堆），
> 生产换成高效分配器后绝对差距会缩小，但「池化后稳态零分配」的结论不变。

改造点：

1. **单遍特征扫描**（`attack.zig::ScanIndex`）：82 条特征（SQLi 30 / XSS 13 / 路径 28 / 命令 11）
   按首字节编入 `[256]Range`（编译期计数排序），逐字节查表 + 第二字节过滤 + 等长比较。
   改造前是同一段文本被 82 个 `std.mem.indexOf` 各扫一遍。
2. **缓冲一次预留**：`percentDecodeInto` / `normalizeLowerBytes` 改为 `ensureUnusedCapacity` +
   `appendAssumeCapacity`，不再逐字节扩容。
3. **IP 名单预编译**（`wafreq.zig::IpSet`）：`/32` 与裸 IPv4 进 `u32` 哈希，CIDR 预解析为
   `{network, mask}`，通配符/字面量分列；匹配只解析请求 IP 一次。
4. **规则 enum 化**（`rules.zig::Op/Member`）：编译期解析成员与操作符，求值走 `switch`。
5. 附带：动作 `off` 的类别不扫描；无 body 不查 `Content-Type`；`stripPort` 单遍回扫；
   `trustedSigned` 三头一次遍历；常量时间比较改用 `zzig.hash.constantTimeEql`。6. **Stage 有界对象池**（`waf.zig::StagePool`，容量 64）：中间件与早拒共用，
   稳态不再每请求新建两个 `ArrayList`；分配失败降级为栈上 Stage，不影响拦截。
7. **限流器分片锁**（`ratelimit.zig`，16 片，按 key 哈希选片）：原来全局单锁 +
   字符串哈希，高并发下所有线程挤一把锁；`setMaxEntries` 按分片分配（每片至少 1）。
8. **早拒统计口径修复**：早拒拦截的请求不会再进路由层，现在在 `checkHead` 拦截分支补记
   一次总数（否则 `blockedRatio` 会算出 > 1，demo 实测曾为 1.5）；早拒放行仍不计数。
**zzig 复用**：`zzig.Strings.containsIgnoreCase`（收编 `wafreq` 与 `bots` 两份自写实现）、
`zzig.hash.constantTimeEql`、`zzig.compat.Mutex/nanoTimestamp`（既有）、`zzig.config.toml`（既有）。
不复用：`zzig.Net.parseCidr`（`/0` panic）、`zzig.url.decode`（严格报错，WAF 需容错）、
`zzig.glob`（IP 通配符语义不同）、`zzig.json`（规则树递归结构）。

**一次性成本**：构建 100 万条 IP 名单约 **1439 ms**（配置加载/热重载期，不在请求路径）。
热重载由请求线程同步执行，大名单场景会造成一次可感知卡顿。

## 9. 限流功能（两套）与已知缺口

| 能力 | 实现 | 参数 / 配置 | 行为 |
| --- | --- | --- | --- |
| CC 限速 | `ratelimit.zig::WindowLimiter` | `Config/Waf.toml` 的 `rateLimitPerMin`（默认 300） | 每 IP 首次命中起 60 秒固定窗口；超限 429 + `Retry-After`；放行类机器人豁免、静态资源不计数 |
| 接口级限流 | `throttle.zig` | `Config/Throttle.json`（规则 → 阀门两层） | 7 策略 / 多阀门 `priority` / `whenNull` / 429 三格式 / `Api-Throttle-Status` 等头；`middleware()` 或 `guard()` 接入 |

实测：直接调用 `checkRouteRequest` 并显式传 `remote_addr`，`rateLimitPerMin=10` 时
连续 12 次结果为 `200×10 → 429×2`。

**已知缺口（阻断 IP 维度）**：`zzig.http_server.RequestView` 无对端地址，`zzig.web.App.serverHandler`
未填 `Request.remote_addr` → 走 `web.App` 接入时 `ip == ""`：
CC 按设计不计数、`IpSet` 名单不命中、`throttle` 的 `ip` / `whenNull=intercept` 取不到值。
实测 demo 连续 12 次正常请求全部 200、日志 `IP=` 为空。修复点在 zzig（`RequestView` + `serverHandler`），
需跨仓库回归。

## 10. 后续可做
