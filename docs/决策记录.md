## （一）移植：用 Zig 实现 Pek.RWaf / Pek.WAF 的功能（2026-11-17）

**用户原话**：

> 「G:\Code\Rust\Pek.RWaf 和 G:\Code\Pek.FrameWork\Pek.WAF 这两个项目你要帮我参考一下，
> 我要使用 zig 来实现同样的功能并会用到 zig 开发的项目中的。」

**结论**：

1. 功能集合以 **Rust `Pek.RWaf`** 为准（决策链 / 爬虫分级 / 攻击特征 / CSRF / IP 名单 / CC 限速 /
   接口级限流 / 运行统计 / 热重载 / 早拒），规则格式以 **C# `Pek.WAF`** 的 Ruleset JSON 为准。
2. 形态：`zzig` 中间件（`router.useMiddleware(waf.middleware())`）+ `ServerGuard` 早拒
   （因为 zzig 的 `dispatch` 先匹配路由再跑中间件，未匹配路径进不了 WAF）。
3. 复用：`zzig.config.toml`（TOML 解析）/ `zzig.Logger` / `zzig.compat`（Mutex、nanoTimestamp）/
   `zzig.web.router` / `zzig.http_server`；正则用生态既有 `ZZUI/src/regex.zig` **字节级拷贝**（SHA256 已核对）。
4. 不复用并写明原因：`zzig.Net.parseCidr`（`/0` 实测 panic）、`zzig.url.decode`（非法转义报错）、
   `zzig.config.toml.decode`（会清空调用方预设）。
5. 有意的差异（详见 `docs/设计说明.md` §4）：规则集/限流配置用 JSON；`whenNull=intercept` 直接以 IP 作空值标识；
   `jsonDgResult` 省略 `operationTime`/`id`；IP 未知时不计数 CC。

**验证**：`zig build test` → 49/49 通过；`zig build` 通过；`zig build demo` + curl 实测
（浏览器 UA 200、`sqlmap` 403、SQLi 403、`/.env` 与 `/ping.php` 403（早拒）、跨站 POST 403、同源 POST 200）。

## （三）100 万口径性能分析与 zzig 复用；限流功能核查（2026-11-18）

**用户原话**：

> 「当前项目按100万来分析，性能是否有提升以及提取和使用zzig的公共方法。」
> 「每请求 77 次特征扫描？」
> 「当前这个也实际限流相关的功能么？我记得Rust版本的是有限流功能的。」

**结论 1：特征扫描条数是 82 条，不是 77 条（前一表述说少了，纠正）**

- `sqli_patterns` 30 + `xss_patterns` 13 + `path_patterns` 28 + `cmd_patterns` 11 = **82**（`src/attack.zig` L38/L72/L89/L121）。
- 改造前 `bitsOf` 对四组各调一次 `hitAny`，`hitAny` 内部是 `std.mem.indexOf`：
  **同一段 `path + "?" + query + " " + body预览` 被 82 个 `indexOf` 各从头扫一遍**。
- 例外：静态资源只查路径类（28 条）；命中 `skipAttackPrefixes` 整段跳过；每组命中即停。

**结论 2：四项改造 + 三项附带优化，已实测**

1. **单遍特征扫描**（`src/attack.zig::ScanIndex`）：把 82 条特征按「首字节 → 桶」编进
   `[256]Range` 表（编译期计数排序），扫描时逐字节查表，仅当首字节命中且**第二字节**一致时才做等长比较；
   新增对照用例「首字节索引扫描与逐条 indexOf 语义等价」（20 组样本 × 3 种 mask）。
2. **临时缓冲一次预留**：`percentDecodeInto` 用 `ensureUnusedCapacity(input.len)` +
   `appendAssumeCapacity`；`normalizeLowerBytes` 用 `ensureTotalCapacity(总长)` +
   `appendAssumeCapacity`（原来逐字节 `append`，1 KB 文本要经历约 10 次扩容）。
3. **IP 名单预编译**（`src/wafreq.zig::IpSet`）：精确规则存 `u32` 哈希（`/32` 与裸 IPv4），
   CIDR 存预解析 `{network, mask}`，通配符/字面量分列；匹配只解析请求 IP 一次。
   原实现每条规则都要 trim→找 `/`→解析 IPv4，100 万条时单请求即 100 万次字符串解析。
4. **规则操作符/成员 enum 化**（`src/rules.zig::Op/Member`）：编译期解析，求值走 `switch`，
   不再每条规则做 6~10 次 `std.mem.eql` 字符串比较。
   附带：`cfg` 中动作为 `off` 的类别不再参与扫描；无 body 的请求不再查 `Content-Type`；
   `stripPort` 从「三遍扫描」改为「尾部单遍回扫」。
5. **zzig 复用（本轮真正落地的）**：
   - `wafreq.containsIgnoreCase` → 转调 `zzig.Strings.containsIgnoreCase`（本仓旧实现删除）；
   - `bots.hitAnyIgnoreCase` 的逐字节循环 → `zzig.Strings.containsIgnoreCase`；
   - `trustedSigned` 的常量时间比较 → `zzig.hash.constantTimeEql`；
   - `waf.zig::headerOf` 与 `wafreq.headerOf` 两份遍历合并为一份（`wafreq.headerOf`，`waf.zig` 转调）；
   - `trustedSigned` 三个签名头从三次遍历合并为一次。
   - **仍不复用（有据）**：`zzig.Net.parseCidr`（`/0` panic）、`zzig.url.decode`（非法转义报错，
     WAF 需要容错扫描）、`zzig.glob`（按 `/` 分段，IP 通配符按 `.` 分段语义不同）、
     `zzig.json`（规则树是递归结构，`std.json.Value` 树形解析更合适）。

**实测（`zig build bench -Doptimize=ReleaseFast`，Windows / Zig 0.17.1，100 万次判定）**

| 场景 | 改造前 | 改造后 | 变化 |
| --- | --- | --- | --- |
| allow: browser GET | 6826.8 ns | **365.6 ns** | 18.7× |
| block: sqli query | 3990.9 ns | **510.5 ns** | 7.8× |
| block: malicious UA | 238.6 ns | 247.0 ns | 持平（早拦，未进扫描） |
| allow: static asset | 1429.6 ns | **272.0 ns** | 5.3× |
| allow: POST 8KB body | 未跑完（82×8KB×100 万 ≈ 656 GB 扫描量） | **23.98 µs** | 从不可测到 4.17 万/s |
| 1M IP 黑名单 miss（200 次） | O(n) 字符串解析 | **204.5 ns** | 数量级 |
| 1000 条规则 miss（10 万次） | — | **3.20 µs** | — |
| CC 计数开启 | — | **214.9 ns** | 增量约 25 ns |

- 构建 100 万条 IP 名单（`IpSet.build` + 字符串构造）**1439 ms**：属于配置加载/热重载的一次性成本，
  不在请求路径上；热重载由请求线程同步执行，大名单场景需知悉这一次性卡顿。
- 回归：`zig build test --summary all` → **51/51 通过**（基线 49 + 新增 2 个等价性用例）。

**结论 3：限流功能存在且两套，均已实现 + 有单测；但 `web.App` 接入时 IP 维度不生效**

- **CC 限速**：`Config/Waf.toml` 的 `rateLimitPerMin`（默认 300），`ratelimit.zig::WindowLimiter`
  「每 IP 首次命中起 60 秒」固定窗口，超限 429 + `Retry-After`；放行类机器人豁免、静态资源不计数；
  单测 `窗口限速基本语义` / `窗口到期后重置` / `容量上限下不无限增长`。
- **接口级限流**：`throttle.zig`，对齐 C# `DH.RateLimter` 与 Rust `Pek.RWaf::throttle`；
  `Config/Throttle.json` 两层结构（规则 → 阀门）、7 策略（ip/userIdentity/header/query/requestPath/cookie/form）、
  多阀门按 `priority` 降序、`whenNull`、429 三种返回体、`Api-Throttle-Status` / `Retry-After` /
  `X-RateLimit-Limit` / `X-RateLimit-Remaining`；接入方式 `throttle.middleware()` 或 `throttle.guard(rule, handler)`；
  单测 6 个（`IP 策略限流与 429 返回体`、`whenNull`、`多阀门按 priority 降序`、`配置加载与热重载`、`guard` 等）。
- **实测验证（直接调用 `checkRouteRequest` 并显式传 `remote_addr`）**：
  `rateLimitPerMin=10` 时连续 12 次 → `200 200 200 200 200 200 200 200 200 200 429 429`（第 11 次起 429）。
- **缺口（实测发现）**：`zzig.http_server.RequestView` **没有对端地址字段**，`zzig.web.App.serverHandler`
  也未填充 `Request.remote_addr` → 走 `web.App` 接入时 `ip == ""`：
  - CC 按设计「IP 未知不计数」→ 不生效；
  - `IpSet` 名单匹配空 IP 返回 false → IP 白/黑名单不生效；
  - `throttle` 的 `ip` 策略与 `whenNull=intercept` 取不到 IP。
  实测：demo（`web.App` 接入）连续 12 次正常浏览器 UA 请求全部 `200`，日志 `IP=` 为空。
  **修复需改 zzig 公共库**（`RequestView` 增加对端地址 + `serverHandler` 透传），涉及所有消费方回归，
  按「跨仓库改动先确认」列为待办，不在本轮擅自动手。

**验证命令**：

```text

```

### （三·续）Stage 池化、分片限流、早拒统计修复（2026-11-18，用户「请继续」）

**用户原话**：

> 「请继续」

**结论与实测**：

1. **Stage 有界对象池**（`src/waf.zig::StagePool`，容量 64）：`middlewareInvoke` 与
   `ServerGuard.invoke` 不再每请求 `Stage{}` + `deinit`（两个 `ArrayList` 次次重新分配/扩容）。
   用 `threadlocal` 不行——zzig 是 thread-per-connection，线程退出时堆缓冲不会自动释放。
   实测（bench，`page_allocator`）：复用 **349.1 ns/次** vs 每请求新建 **3257.6 ns/次**（9.3×）。
   注：换高效分配器后绝对差距会缩小，「池化后稳态零分配」结论不变。
2. **限流器分片锁**（`src/ratelimit.zig`，16 片，按 key Wyhash 选片）：原来全局单锁 + 字符串哈希，
   高并发下所有线程挤一把锁。`max_entries` 改为 `setMaxEntries(total)` 按分片分配（每片至少 1）。
   实测（8 线程 × 20 万次，key 分散）：**23.3 ns/次 ≈ 4286 万次/秒**。
   CC 阈值行为不变：`rateLimitPerMin=10` 仍是 `200×10 → 429×2`。
3. **早拒统计口径修复**（`src/waf.zig::checkHead`）：早拒拦截的请求不会再进路由层，
   原来不计入 `total`，导致 `blockedRatio` 可能 > 1（demo 实测 **1.5**）。
   现在拦截分支补记一次 `recordRequest()`，早拒放行仍不计数（避免与路由层重复）。
   实测 demo：`total=4 blocked=2 ratio=0.5`；新增用例「早拒拦截补记请求总数（拦截率不超过 1）」。
   同时 `checkHead` 补上 `maybeReload()`（早拒层也能触发热重载，10 秒节流）。

**回归**：`zig build test --summary all` → **52/52 通过**；`zig build` 通过；
demo 端到端：`ping=200`、`sqlmap=403`、`/.env=403`（早拒）、SQLi=403、`/__stats` 正常。

### （三·续二）zzig 透传对端地址，IP 维度在 App 接线下生效（2026-11-18，用户「继续」）

**用户原话**：

> 「涉及到修改的都需要提交，另外继续」

**结论**：

1. **zzig 改动**（`G:\Code\Zig\zzig`）：
   - `http/server.zig::RequestView` 新增 `remote_addr: ?[]const u8 = null`；
   - `serveOne` 从 `accept` 返回的 socket 地址填充（Windows `RemoteAddress` / POSIX `accept` 的
     peer 参数同口径），格式 `ip:port`（IPv6 为 `[::1]:port`）；
   - `http/web.zig::serverHandler` 透传到 `router.Request.remote_addr`；
   - 端到端用例新增断言「对端地址非空且以 `127.0.0.1:` 开头」。
2. **踩坑（Zig 0.17 格式化）**：`IpAddress` 只实现了新 `Io.Writer` 接口
   （`format(a, w: *Io.Writer)`），`std.fmt.bufPrint(&buf, "{}", .{addr})` **不会报错**，
   而是退化成结构体调试打印（实测输出 `.{ .ip4 = .{ .bytes = { 127, 0, 0, 1 }, .port = 60917 } }`）。
   正确写法：`var w: std.Io.Writer = .fixed(&buf); addr.format(&w); w.buffered()`。
3. **实测（demo，`web.App` 接入，`rateLimitPerMin=10`）**：连续 12 次正常浏览器 UA 请求 →
   `200 200 200 200 200 200 200 200 200 200 429 429`；日志
   `[WAF] 拦截 GET /ping 状态=429 IP=127.0.0.1 ... 原因=请求频率超限（10 次/分钟）`。
   （修复前：同场景 12 次全 200、日志 `IP=` 为空。）
